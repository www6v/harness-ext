## 1. 系统概述

DeepSeek Harness（`@deepseek-ai/dsh-root`）是一个**全 plugin 化的 Cordis agent harness**——基于 Cordis 框架的 AI agent 应用平台。它是一个包含 100+ workspace package 的 monorepo，分为 `packages/`（capability seam）、`apps/`（CLI、Web 前端、desktop 应用）和支持基础设施。Agent loop 通过 plugin 架构驱动 LLM 进行 tool 调用，每个 capability 都是一个 Service Definition / Provider / Consumer 三元组。

系统有专门的 **`docs/defensive-patterns.md`** 文件，记录了从真实生产 bug 中总结出的 defensive patterns。

## 2. LLM 请求 retry 机制

**核心 package：** `packages/llm/llm-retry/`（`@deepseek-ai/dsh-llm-retry`）

> **解决的问题：** 当模型 API 请求因瞬时故障（rate limit、server error、network timeout、transport error）而失败时，agent turn 会直接终止，用户需要手动重试整个对话。这在高频调用场景中严重降低可用性。
>
> **目的：** 在 agent-loop 的 `agent/request-error` waterfall 上自动截获可恢复的失败，在同一个 open turn 内透明重试失败的 step，使上层业务和最终用户对瞬时故障无感知。

### 2.1 设计原则

- **durable before wait**：retry 记录（`llm/retry` event）在启动任何 timer 之前就写入 session log。如果进程崩溃，retry 意图被保留并可以重放。
- **open-step boundary**：在 agent loop 的 `agent/request-error` waterfall 上运行恢复，而不是包装 `ctx.llm.stream()`——raw stream 无法将已发出的 chunk 与 durable 层分离，而 loop 可以在同一个 open turn 内重新运行失败的 step。

### 2.2 两种 retry 模式

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| **normal** | 有限预算（默认 5 次），仅对特定 error code 重试 | 运行时控制预算的场景 |
| **always** | 无限 retry 直到成功、cancellation 或 disposal | 需要最高可用性的场景 |

**可 retry 的 error code：** `EMPTY_RESPONSE`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`

### 2.3 Exponential backoff 与 jitter

```typescript
// 来自 packages/llm/llm-retry/src/index.ts
function localDelay(config: ResolvedRetryPolicy, retry: number, random: () => number): number {
  const exponent = Math.min(retry - 1, 1024)
  const exponential = Math.min(config.initialDelayMs * 2 ** exponent, config.maxDelayMs)
  const jitter = 1 - config.jitterRatio + 2 * config.jitterRatio * random()
  return Math.min(exponential * jitter, config.maxDelayMs)
}
```

默认参数：初始 500ms → 最大 10s，jitter 比例 10%。

### 2.4 Provider `Retry-After` 支持

如果 Provider 返回有效的 `Retry-After` header 且在 policy 范围内，用它替代本地 backoff 时间；超过 `maxDelayMs` 时 fallback 到本地 policy。

### 2.5 Retry 历史持久化

```typescript
// 来自 packages/llm/llm-retry/src/history.ts
// 通过 session projection 跟踪每个 provider+policyKey 的 retry 计数
// retry 计数仅在相同 provider 和完整 policy key 的 event 间延续
```

### 2.6 配置示例

```yaml
- name: '@deepseek-ai/dsh-llm-deepseek'
  config:
    apiKeyEnv: DEEPSEEK_API_KEY
    retryPolicy:
      mode: always
      backoff:
        initialDelayMs: 1000
        maxDelayMs: 30000
        jitterRatio: 0.2

- name: '@deepseek-ai/dsh-llm-retry'
```

### 2.7 Invariant 校验

`packages/llm/llm-retry/src/invariant.ts` 在 runtime 校验：
- 每个 `llm/retry` event 的 turn、step、provider、policy 匹配
- 每个 `llm/retry-started` 必须与一个之前的预约尝试配对
- `retryId` 在同一 chain 中保持一致
- retry 次数在 normal 模式下不超过 `maxRetries`

## 3. Tool call timeout

**核心 package：** `packages/guard/timeout-policy/`（`@deepseek-ai/dsh-tool-call-timeout-policy`）

> **解决的问题：** Tool（如 `web_fetch`、`web_search`、`bash`）可能在网络阻塞、死循环或远程无响应时无限期挂起，导致整个 agent turn 卡死，用户永远得不到响应。
>
> **目的：** 为声明了 `timeoutMs` 的 tool 提供协作式 deadline 保护——超时后通过 `exec.signal` 通知 tool 终止，并将结果映射为结构化的 `TOOL_TIMEOUT` error，让模型能够据此决策（retry、调整参数或放弃）。

### 3.1 设计原则

- **Cooperative，非 hard kill**：timeout 仅通过 `exec.signal` 通知，tool 自行处理终止
- **每个 tool 自行声明 timeout 预算**：`timeoutMs` 定义在 `ToolDefinition` 上
- **Scoped classification**：`TOOL_TIMEOUT` 同时作为内部分类码和结构化 error code，与外部 deadline 产生的普通 cancel 区分开

### 3.2 执行流程

```
deadline 触发 → abort(exec.signal) → 下游代码响应 cancellation → next() 完成
→ 返回 "Error: tool call timed out after <ms>ms" 给模型
```

### 3.3 组合支持

多个 `tools/execute` listener 通过 Cordis 注册顺序组合：
- **外层注册**的 timeout 包裹整个 retry 操作
- **内层注册**的 timeout 仅包裹单次尝试

### 3.4 已知限制

- tool 忽略 cancellation signal 时无法强制停止——caller 会一直等待
- `bash`、`read`、`write`、`edit` 等已发布 tool 不声明 timeout

## 4. Event-sourced session log（崩溃恢复基础）

**核心 package：** `packages/core/session/`（`@deepseek-ai/dsh-session`）

> **解决的问题：** Agent 对话过程中如果进程崩溃、被 kill 或断电，所有对话历史和进行中的 tool 调用结果都会丢失。即使有持久化，如果写了一半就中断，也会产生损坏的不可恢复数据。
>
> **目的：** 将所有模型可见的事实以 append-only event 的形式持久化到 session log 中，使任意时刻崩溃后都能从 log 精确重建对话状态；对中断的 turn 注入语义明确的修复 event（`TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN`），让模型在 resume 时能做出安全决策。

### 4.1 核心设计

```
Model-visible ⟺ logged（runtime invariant 强制执行）
```

- 每个模型可见的事实都记录在 **append-only** 的 event log 中
- `deriveMessages()` 从 log 投影模型历史——log 是唯一的 source of truth
- Surface projection 支持通过 replacement 操作进行 compaction，隐藏被取代的条目但保留原始 event

### 4.2 崩溃修复机制

在 resume 时，系统会检查中断的状态并注入修复 event：

| 场景 | 修复方式 |
|------|----------|
| 存在 assistant tool request 但没有 `tool/call` | 注入 `TOOL_NOT_STARTED` result："The tool call was interrupted before the Harness recorded it as started. Retry it if it is still needed." |
| 存在 `tool/call` 但没有 result | 注入 `TOOL_OUTCOME_UNKNOWN` result："The tool call was interrupted after it was recorded, but no result was durably recorded. Its outcome is unknown. Decide whether to retry from the tool semantics: retry only if the operation is read-only or idempotent; if it may have side effects, first verify external state or ask the user. Do not retry blindly." |

### 4.3 格式迁移安全

- `SESSION_FORMAT_VERSION` 标记当前 logical format
- 相邻 migration package 处理历史格式转换
- Write open 只发布当前 format 的 successor generation
- 已 committed 的 generation path 永不 rename、replace 或 delete

### 4.4 写入互斥

同一个 session 只存在一个 write handle；并发的 resume 被拒绝。

## 5. Cancellation 与 graceful degradation

**核心 package：** `packages/core/agent-loop/`（`@deepseek-ai/dsh-agent-loop`）

> **解决的问题：** 在 agent 运行过程中，用户可能中途取消操作、plugin 可能被 unload、factory 可能需要 shutdown。如果没有统一的 cancellation 机制，这些异步终止信号会以不可预测的方式交织，导致 state 不一致（如 agent 已被 remove 但 session 还在运行）、stream 文本丢失、tool call 孤儿执行等问题。
>
> **目的：** 建立从 setup → run → teardown 全生命周期的 cooperative cancellation 体系：融合多个 cancellation source 的信号，确保取消过程中的中间状态（已输出的 stream 文本、已 dispatch 的 tool 结果）被正确保留，teardown 达到 quiescence 后才返回。

### 5.1 Cancellation 机制

Agent loop 在整个生命周期中实现 cooperative cancellation：

- **Stream 保留**：在 stream 中途 cancel 时，已交付的部分文本作为 `interrupted: true` anchor 保留——user 看到已到达的内容
- **Synthetic tool result**：cancellation 后未 dispatched 的 tool call 获得 `ABORTED_BEFORE_DISPATCH` result pair
- **Fused cancellation signal**：setup、caller 和 factory 的 disposal signal 融合在一起——任何来源的 race 都被干净处理
- **Exclusive tool barrier**：`maxParallelToolCalls` 限制并发；exclusive call 单独运行作为排序 barrier
- **Memoized quiescence boundary**：disposal 流程为 `dispose()` → cancel 所有工作 → await 子项、scope 和 registration 的 quiescence → 然后返回。每个 detach 绑定到精确的对象 id，因此过时的 disposer 无法移除后来的同名替换

### 5.2 Disposal 流程

```
dispose()
  → abort(new Error('lifecycle disposed'))
  → 移除所有 event listener
  → machine.cancel({ kind: 'disposed' })
  → await machine.scope.dispose()       // 等待 scope 内的所有 effect 释放
  → unregister from agent/session registries
  → close session write handle           // drain buffer
  → 返回（quiescence 达成）
```

### 5.3 创建事务回滚

创建是一个受 rollback 保护的 transaction：
1. 构造私有 session、agent 和 scope context
2. 运行可选的 setup
3. 进入 registry
4. 宣布 `session/created` 然后 `agent/created`
5. 启动 driver

任何步骤的失败触发完整 rollback，不发布任何 id。

## 6. Atomic file write 与跨进程 lock

**核心 package：** `packages/util/atomic-write/`（`@deepseek-ai/dsh-atomic-write`）

> **解决的问题：** 配置文件（settings、credentials 等）在被写入时如果进程崩溃或并发写入，会导致文件内容部分损坏或数据丢失。此外，可预测的临时文件路径可能被 symlink 攻击劫持，导致任意文件被覆盖或权限提升。
>
> **目的：** 提供 write-to-temp-then-rename 的原子替换语义，保证 reader 始终看到旧版本或新版本的完整内容，永远看不到部分写入。同时提供跨进程 file lock 串行化 read-modify-write 操作，防止并发写冲突。

### 6.1 Atomic write

```typescript
// 来自 packages/util/atomic-write/src/index.ts
export async function writeFileAtomic(filename, content, options) {
  const temp = `${filename}.${randomBytes(6).toString('hex')}.tmp`
  await writeFile(temp, content, { mode: options.mode, flag: 'wx' })  // exclusive create
  await renameAtomicTemp(temp, filename)
}
```

安全性保障：
- **Exclusive create**（`wx` flag）——拒绝跟随 symlink，防止在可猜测的临时路径上植入 symlink
- **同目录 rename**——保持在同一个 filesystem 上，确保原子性
- **Permission 收窄**：临时文件带有 caller 声明的 `mode` 并随 rename 保留——不存在 chmod race

### 6.2 Windows retry

Windows 上的 rename 可能会因为杀毒软件等瞬时占用导致 `EACCES`/`EBUSY`/`EPERM`，系统使用 bounded exponential backoff 进行 retry：

```typescript
const WINDOWS_RENAME_RETRY_LIMIT = 8
const WINDOWS_RENAME_RETRY_INITIAL_MS = 20
```

### 6.3 跨进程 file lock

`withFileLock` 通过 `<filename>.lock` sibling 文件协调 read-modify-write 循环：

```typescript
const LOCK_RETRY_INITIAL_MS = 20
const LOCK_RETRY_MAX_MS = 200
const DEFAULT_LOCK_WAIT_MS = 2_000
```

- **Contender 从不删除 lock 文件**——文件年龄无法证明 owner 已停止，需操作员手动恢复
- **Reader 不持 lock**——rename commit 是原子操作，无需锁定读取

### 6.4 已知限制

- **Atomic 但不 durable**：不调用 `fsync`，崩溃后 rename 可能被回滚
- **仅支持 string 内容**：无 Buffer 或 stream 形式
- **Orphaned lock 需要人工恢复**

## 7. Client connection 恢复

**核心 package：** `packages/client/connection/`

> **解决的问题：** Browser 端与 Host 端之间的 WebSocket connection 可能因网络抖动、Host 重启、代理超时等原因断开。如果没有自动重连机制，用户需要手动刷新页面，导致正在进行的对话中断和 UI 状态丢失。
>
> **目的：** 在 connection 断开时自动使用 exponential backoff 重连，建立新的 generation 后通过 `connection/reset` event 通知所有依赖方重新拉取数据，使用户体验不因瞬时网络问题而中断。

### 7.1 ConnectionController

`ConnectionController` 管理 browser ↔ host 之间的 WebSocket connection：

```typescript
// 来自 packages/client/connection/src/client/connection.ts
private backoffCap(attempt: number): number {
  const { backoffBaseMs, backoffFactor, backoffMaxMs } = this.config
  return Math.min(backoffMaxMs, backoffBaseMs * backoffFactor ** Math.max(0, attempt - 1))
}

private backoffDelay(attempt: number): number {
  const cap = this.backoffCap(attempt)
  return cap / 2 + Math.random() * (cap / 2)  // 50-100% jitter
}
```

### 7.2 可配置参数

| 参数 | 默认值 | 作用 |
|------|--------|------|
| `backoffBaseMs` | 500 | 首次 retry 延迟上限 |
| `backoffFactor` | 2 | 每次失败的增长因子；1 表示固定上限 |
| `backoffMaxMs` | 10,000 | 最大 retry 延迟上限 |
| `generationReadyWarnMs` | 3,000 | 慢 handshake 警告（不 cancel） |
| `generationReadyTimeoutMs` | 15,000 | Handshake hard deadline |

### 7.3 关键特性

- **手动 reconnect**：`reconnect()` 重置 attempt counter 并立即 retry
- **网络感知**：`setNetworkAvailable(false)` 暂停 retry；恢复后从初始 backoff 开始
- **状态去重**：相同的连续 state transition 被 suppressed
- **Sink 异常隔离**：listener 抛出异常仅记录，不杀死 reconnect loop
- **`connection/reset` event**：所有基于 connection 的 cache 在新 generation 建立时必须重新拉取

## 8. Process 生命周期与退出保证

**核心 package：** `packages/subprocess/subprocess-local/`（`@deepseek-ai/dsh-subprocess-local`）

> **解决的问题：** Agent 通过 `bash`/`pwsh` 等 tool 启动的子进程可能在 agent session 结束后继续运行（orphan process），或进程树中的一个子孙脱离管控范围后无法被 terminate。此外，如果子进程的环境变量携带了 Harness 的 API key 等 credential，可能通过 `env` 命令或 core dump 泄漏。
>
> **目的：** 为每个子进程建立从 spawn 到 quiescence 的完整管控链路：在启动前先选择 OS 级 containment（Linux user-systemd scope / Windows Job object），确保 kill 信号覆盖整个进程树；擦除 credential 环境变量；在 Harness 进程异常退出时同步终结所有子进程。

### 8.1 核心规则

> Dispose must reach quiescence, not just request it.
> —— `docs/defensive-patterns.md`

### 8.2 Process 管理的安全保障

- **先隔离后执行**：在用户命令运行之前先选择 containment 机制（Linux user-systemd scope、Windows Job object）
- **Fallback 不 retry**：原生 containment 失败直接报告；Provider 绝不在可能已部分启动后通过 fallback 机制重新执行命令
- **PID 重用保护**：Fallback 的 process identity 携带 start time，因此清理操作不会跟随被回收的 PID
- **环境变量擦除**：子进程环境中删除 `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*`
- **安全的 spill file**：`0600` permission、exclusive open、随机名称、`0700` 每进程目录——防止共享 temp 目录中的 symlink race

### 8.3 退出处理

- **正常 disposal**：terminate 所有正在运行的 managed range 和 terminal session，await quiescence
- **同步 finalization**（`process.exit()`、uncaught exception）：创建零个 Promise 或 timer，保留 exit code，包含每个 target 的 failure
- **`SIGKILL`、fatal OOM、native crash、断电**：需要外部 supervisor

## 9. Defensive patterns

**文档：** `docs/defensive-patterns.md`

> **解决的问题：** 这些规则来自 Harness 开发过程中实际出现过的 bug 类别——每个 pattern 对应一类曾经"差点上线"或在早期版本中出现过的 defect。如果没有这些规则，同类错误会在不同的 lifecycle/concurrency/subprocess/teardown 代码中反复出现。
>
> **目的：** 将这些经验教训固化为可执行的编码规则，在 CR 和开发时被引用，防止已知 bug class 的复发。

### 9.1 独立报告正交结果

> 一个结果可以同时是多件事——一个 process 可以 timed out **且** exit code 为 0，因为它捕获了 signal。

将每个独立事实（`timedOut`、`signal`、`exitCode`）放到自己的字段上；绝不在一个 flag 的 branch 内嵌套报告另一个 flag。

### 9.2 在公共 API 的两端履行 contract

> 当实现接收同一个结果的多种表示时，在通过公共 API 返回之前将其 normalize。

示例：`LlmAdapter.stream()` 的实现可能 throw exception 或 emit `finish {kind:'error'|'aborted'}`，但 `LlmRuntime.stream()` 仅将模型请求失败作为 terminal finish chunk 暴露；middleware 和 consumer 的 defect 保持为 throw。这使 consumer 无需猜测捕获的 exception 来自 Provider、wrapper、chunk log 还是自己的 assembly。

### 9.3 Async state 不是 synchronous state

> `agent.followup()` 没有 per-message 的 completion 或 result；background job 的 completion 与 turn boundary 存在 race；`reader.close()` 对 EOF 和 disposal 都会触发。

绝不要将 `agent/status` 或 `whenIdle()` 当作一个 follow-up 的 result：多个 queued follow-up、steering 和 injected work 可能共享一个 `running` 区间。

### 9.4 Dispose must reach quiescence

> 发起 kill/abort 但在工作停止之前返回的 disposal 会留下 orphan process。

使 cleanup async 并 await child process 退出（kill → await `done`），且在 kill 之前 close listener/notification registry，以便 late completion 保持静默。

### 9.5 在 dispatcher 中包容 callback exception

> 用户提供的 listener 抛出 exception 绝不导致其所在的 Promise 被 rejected，也不应使其后的 listener 无法执行。

将 dispatch loop 包装在 try/catch 中并 log；一个坏的 subscriber 绝不破坏核心 lifecycle。

### 9.6 绝不将 untrusted output 暴露给环境变量或可预测路径

> Spawn 的命令获得经过擦除的环境变量（删除 `*KEY*`/`*SECRET*`/`*TOKEN*`/`*PASSWORD*`），因此 Harness credential 不会泄漏到 output、`env` 或 spill file 中。

Temp/spill file 使用 private（0700）目录、随机名称和 exclusive owner-only open（`'wx'`、`0o600`）——可预测的 world-readable 路径会引发 symlink race 和信息泄漏。

### 9.7 Unlink link-shaped path

> 可能为 symlink 或 Windows junction 的 path，使用 `lstatSync().isSymbolicLink()` 检查后 `unlinkSync()` 删除

`unlink` 只删除 link 本身并拒绝真实目录，因此永远不会 follow link 进入其 target。Windows 上对 junction 使用 `rmSync(link)` 会抛出 `ERR_FS_EISDIR`；recursive deletion 可能穿越 junction 进入其 target。保留 recursive `rmSync` 仅用于已知的真实目录。

## 10. HTTP proxy 容错

**核心 package：** `packages/util/http-proxy/`（`@deepseek-ai/dsh-http-proxy`）

> **解决的问题：** 企业环境中用户通过 `HTTPS_PROXY` 等环境变量配置了 HTTP proxy。如果 Harness 忽略了这些配置，LLM API 调用和 web fetch 将无法连接外网。反之，如果 proxy 配置了不受支持的 scheme（如 SOCKS），Harness 不能因此拒绝启动——因为该变量可能是为其他工具设置的。
>
> **目的：** 在 process 启动时一次性解析标准 proxy 环境变量，注入 `globalThis.fetch` 的 dispatcher，使所有 HTTP 流量（LLM、web search、MCP transport）自动走 proxy；对不可用的 proxy scheme 报告后跳过，不阻塞启动。

### 10.1 设计原则

- **一次解析，一个 matcher**：`proxyForUrl()` 和安装的 dispatcher 调用同一个函数——policy 和执行之间不存在 drift
- **不可用的 proxy → 跳过而非崩溃**：SOCKS/PAC URL 或无法解析的值被 report 后直接连接，不阻止 agent 启动
- **Loopback 始终 bypass**：`localhost`、`127.0.0.0/8`、`::1`、`0.0.0.0` 绝不通过 proxy 路由

### 10.2 Egress test gate

每个 outbound call site 都带有 `egress.spec.ts` 测试——通过 fake proxy 驱动真实代码路径并断言 proxy 看到了该请求。这是唯一能捕获 SDK 静默更改底层 transport 的方式。

### 10.3 已知限制

- OTLP telemetry exporter 通过 `node:http` 直接发送——不会也不应被 proxy
- SDK 构建自己的 transport（如 E2B）需要显式传递 proxy URL
- 构造 `new Agent(...)` 并作为 `dispatcher` 传递会静默 bypass proxy

## 11. 错误分类体系

**核心 package：** `packages/llm/llm/`

> **解决的问题：** 模型请求失败的原因多种多样（认证失败、速率限制、服务器错误、上下文超限……），如果所有错误都被笼统地当作"调用失败"处理，上游 retry 逻辑无法做出正确的决策——比如对 `AUTH` 错误重试是浪费资源，而对 `RATE_LIMIT` 不重试则降低可用性。
>
> **目的：** 建立统一的 `HarnessError` 体系和规范 error code 集合，使每个 failure 携带机器可路由的 `code`，retry policy 和 error handler 可以基于 code 做精确的 branch 决策。

### 11.1 HarnessError

```typescript
// 来自 packages/llm/llm/src/error.ts
export class HarnessError extends Error {
  readonly code: string  // 稳定的机器可路由的 failure 类别
  constructor(message: string, code: string, options?: ErrorOptions) { ... }
}
```

### 11.2 规范 error code

| Error code | 含义 | 是否可 retry |
|--------|------|-----------|
| `EMPTY_RESPONSE` | 模型返回空响应 | 是 |
| `RATE_LIMIT` | 速率限制 | 是 |
| `SERVER` | 服务器错误 (5xx) | 是 |
| `TIMEOUT` | 请求超时 | 是 |
| `TRANSPORT` | 传输层错误 | 是 |
| `AUTH` | 认证失败 (401/403) | 否 |
| `INVALID_REQUEST` | 无效请求 (400, 413) | 否 |
| `QUOTA` | 配额超限 | 否（always 模式除外） |
| `CONTEXT_WINDOW_EXCEEDED` | Context window 超限 | 特殊处理 |
| `ABORTED` | 请求被 cancel | 否 |

### 11.3 DeepSeek Provider 的错误分类

```typescript
// 来自 packages/llm/llm-deepseek/src/adapter.ts
export function httpErrorCode(status: number, error?: WireError['error']): string {
  if (status === 401 || status === 403) return 'AUTH'
  if (status === 413) return 'INVALID_REQUEST'
  if (isQuotaExceededError(detail)) return QUOTA_EXCEEDED_CODE
  if (status === 429) return 'RATE_LIMIT'
  if (status === 400) {
    if (isContextWindowExceededError(detail)) return CONTEXT_WINDOW_EXCEEDED_CODE
    return 'INVALID_REQUEST'
  }
  if (status >= 500) return 'SERVER'
  return `HTTP_${status}`
}
```

`errorChain()` 函数渲染完整的 `cause` chain，包括 `AggregateError` 成员用于诊断。

## 12. Loop detection 与中断

**核心 package：** `packages/guard/repeat-tool-reminder/`

> **解决的问题：** LLM 有时会陷入"重复调用同一 tool 且参数完全相同"的循环——每次模型都认为"再试一次也许能成功"，但实际上每次都得到相同结果，浪费 token 和时间，用户看到的是对话在无意义地原地踏步。
>
> **目的：** 检测连续重复的 tool call（相同 tool name + canonical 化后的相同 argument），在重复次数达到配置的 threshold 时分阶段提醒模型（gentle → detailed → 更强干预），并在用户新消息到来时自动重置计数。

### 12.1 检测机制

```typescript
const GENTLE_REMINDER = 'You are repeating the exact same tool call with identical arguments...'
```

### 12.2 升级策略

| 重复次数 | 动作 |
|----------|------|
| 3 次 | Gentle reminder |
| 5 次 | Detailed reminder，包含 tool name 和 argument |
| 8 次 | 更强的干预 |

### 12.3 配置选项

- 可配置的 threshold：`[3, 5, 8]`
- Canonical argument 比较（深度 JSON key-sort）
- Include/exclude wildcard pattern 过滤 tool
- User interjection 自动重置计数

## 13. LSP transport 故障转移

**核心 package：** `packages/lsp/lsp-stdio/`

> **解决的问题：** LSP server 进程可能因自身 bug、资源耗尽或 OS 信号而意外退出。如果 agent 正在通过 LSP 获取代码补全或诊断信息，server 的死亡会导致查询失败，而 agent 不知道是因为 server 死了还是查询本身有问题。
>
> **目的：** 对只读 LSP 查询（如 completion、diagnostics）在 transport 故障时透明重试一次——识别 transport 级故障与查询级错误的区别，只对前者替换 dead instance 并重试。

### 13.1 透明 retry

```typescript
// 来自 packages/lsp/lsp-stdio/src/index.ts
let canRetryTransport = true
for (;;) {
  const [queryOutcome] = await Promise.allSettled([instance.query(...)])
  if (instance.dead) {
    await Promise.allSettled([instance.dispose()])
    this.evictIfCurrent(workspaceKey, instance)
  }
  if (queryOutcome.status === 'fulfilled') return queryOutcome.value
  // 只读查询：替换 dead transport 一次并透明 retry
  if (!canRetryTransport || !instance.isTransportFailure(queryOutcome.reason)) {
    throw queryOutcome.reason
  }
  canRetryTransport = false
  instance = this.instanceFor(workspaceKey, workspace)
}
```

### 13.2 分级 teardown

```typescript
// 来自 packages/lsp/lsp-stdio/src/instance.ts
private async tearDown(): Promise<void> {
  const shutdownDeadline = deadline(undefined, this.spec.shutdownTimeoutMs, 'LSP_SHUTDOWN')
  try {
    await this.gracefulShutdown(shutdownDeadline.signal)  // LSP shutdown/exit
  } catch { /* 降级到 force terminate */ }
  finally { shutdownDeadline[Symbol.dispose]() }
  await this.forceTerminate()  // SIGTERM → SIGKILL
}
```

- 可配置的 `shutdownTimeoutMs`（默认 5000）用于 graceful shutdown
- 可配置的 `killGraceMs`（默认 2000）用于 cancel request 的 grace period
- Await process close 以达到 quiescence

## 14. Workflow Worker 隔离与凭证擦除

**核心 package：** `packages/workflow/workflow-worker-thread/`

> **解决的问题：** Workflow script 在 worker thread 中执行用户编写的 JavaScript 代码。如果 worker thread 继承了主进程的完整环境变量，用户的 script 可以通过 `process.env` 读取到 `DEEPSEEK_API_KEY` 等 credential 并外传。此外，worker thread 的 crash 不能影响主进程。
>
> **目的：** 在 worker thread spawn 时构建完全擦除 credential 的环境变量，仅传递必需的 `TMP`/`TEMP` 和 `TSX_TSCONFIG_PATH`，确保用户代码在隔离环境中运行。

### 14.1 环境隔离

```typescript
// 来自 packages/workflow/workflow-worker-thread/src/host.ts
export function workerSpawnEnv(platform, tsconfigPath?): NodeJS.ProcessEnv {
  const env: NodeJS.ProcessEnv = {}
  // 无环境 credential，无 loader flag
  if (platform === 'win32') {
    const tmp = tmpdir()
    env.TMP = tmp; env.TEMP = tmp
  }
  if (tsconfigPath !== undefined) env.TSX_TSCONFIG_PATH = tsconfigPath
  return env
}
```

- Worker thread 以**擦除的环境变量**启动
- Pending start 共享一个 abort signal
- Child 共享 idempotent cleanup

## 15. DNS pinning（SSRF 防护）

**核心 package：** `packages/web/web-fetch-http/`

> **解决的问题：** Agent 通过 `web_fetch` tool 获取用户指定的 URL 内容。如果 agent 获取了 `http://169.254.169.254/latest/meta-data/`（云 metadata 服务）或 `http://127.0.0.1:8080/admin`（内部服务），就会产生 SSRF（Server-Side Request Forgery）漏洞，泄漏敏感信息或攻击内部服务。
>
> **目的：** 在 DNS 解析后、TCP 连接前验证目标 IP 是否为公网地址，拒绝内网地址（private IP、loopback、link-local）；使用 address pinning 确保解析结果在后续连接中不被替换，防止 TOCTOU 攻击。

### 15.1 地址验证

```typescript
// 来自 packages/web/web-fetch-http/src/network.ts
export async function resolvePublicAddresses(hostname, signal): Promise<PublicAddress[]> {
  const resolved = await raceWithSignal(resolver(unbracketed, { all: true, order: 'verbatim' }), signal)
  for (const entry of resolved) {
    if (!isPublicIpAddress(entry.address)) {
      throw new WebError(
        `URL hostname "${hostname}" resolves to a non-public IP address`,
        'WEB_BLOCKED_URL'
      )
    }
  }
  return addresses
}
```

关键安全性：
- **Address pinning**：在连接之前验证 DNS 解析结果；不使用第二次解析
- **NAT64 感知**：通过 transition prefix 验证嵌入的 IPv4
- **Per-request dispatcher**：每个 fetch 有自己独立的 connection pool

## 16. Session projection cache 的 fail-soft 机制

**核心 package：** `packages/session/session-projection-cache/`

> **解决的问题：** Session projection 是从 event log 增量 fold 出的派生状态（如 surface message 列表）。每次 cold read 都完整重放 event log 代价很高。引入 cache 可以加速，但如果 cache write 失败（磁盘满、权限变更）导致整个 agent 启动失败，cache 就成了新的单点故障。
>
> **目的：** 将 cache 定位为纯优化层——write 失败只 warn 不 throw，cache 过期后下次 cold read 多花一点时间重放 event log 即可恢复，cache 永远不是 authority。

### 16.1 设计原则

```typescript
// 来自 packages/session/session-projection-cache/src/index.ts
private async flushSoft(session: Session, trigger: string): Promise<void> {
  try {
    await this.write(session)
  } catch (error) {
    this.ctx.logger.warn(
      `session projection cache: ${trigger} write for "${session.id}" failed (cache stays stale): ${String(error)}`
    )
  }
}
```

丢失的写入只会在下次 cold read 时产生更长的 tail replay——cache 是 fold 的 shortcut，从来不是 authority。

## 17. Callback 异常隔离

> **解决的问题：** Cordis 的 event dispatch 是同步循环通知所有 listener。如果注册在 lifecycle event 上的某个第三方 plugin 的 listener 抛出未处理异常，会中断后续 listener 的执行，导致部分 plugin 收不到 event，系统进入不一致状态。
>
> **目的：** 在所有 event dispatch loop 中 try/catch 每个 listener callback，将异常隔离在单个 subscriber 内部，确保一个坏掉的 listener 不影响其他 listener 和核心 lifecycle。

多个 package 实现了统一的异常隔离模式：

```typescript
// 来自 packages/subagent/subagent/src/lifecycle.ts
for (const callback of ctx.events.dispatch('emit', dispatchArgs)) {
  try {
    const returned: unknown = callback(info)
    void Promise.resolve(returned).catch((error: unknown) => {
      ctx.logger.warn(`subagent: ${name} listener rejected: ${renderThrown(error)}`)
    })
  } catch (error: unknown) {
    ctx.logger.warn(`subagent: ${name} listener threw: ${renderThrown(error)}`)
  }
}
```

这实现了 `docs/defensive-patterns.md` 中的规则：
> "One bad subscriber never breaks core lifecycle."

## 18. Runtime invariant 校验

> **解决的问题：** Session log 和 retry event 等核心数据结构有严格的 structural constraint（如 retry event 必须在 open turn/step 内、tool call 和 result 必须配对）。如果这些 constraint 被破坏，后续的 `deriveMessages()`、resume 等操作会产生非确定性错误或静默数据损坏。单元测试只能覆盖已知路径，而生产环境中的复杂交互可能触发未预期的违规。
>
> **目的：** 将关键的 structural invariant 编码为 runtime check，在生产环境中持续运行。任何违规即时 fail-loud，使问题在第一时间被发现和修复，而不是在后续流程中以难以排查的方式表现出来。

多个 package 发布 `/invariant` companion plugin，在 runtime（而非仅测试时）验证系统是否遵守其 contract：

| Invariant plugin | 验证内容 |
|----------|----------|
| `llm-retry/invariant` | 每个 retry event 的 turn、step、provider、policy 匹配；`llm/retry-started` 与预约的 `llm/retry` 配对 |
| `agent-loop/invariant` | 从 session log 重建 request 的正确性 |
| `session/invariant` | Sequence number 合法；event 在正确的 turn/step 内；tool call 和 tool result 数量配对 |

这些检查在 production 环境中运行——任何偏差都会即时 fail，不会静默通过。

### 19.2 层级关系与数据流

各层之间呈现 **自底向上的依赖关系**，上层依赖下层提供的保证，下层对上层透明：

#### Infrastructure Layer（基础设施层）

位于最底层，为所有上层模块提供文件系统安全和进程间协调的基础保证。对应 package group `packages/util/`。这一层是纯工具库，不感知 agent、session 或 LLM 等业务概念。

- **Atomic file write** 被 `packages/settings/settings-file/` 和 `packages/credentials/credentials-local/` 直接消费，确保配置和凭证文件写入的原子性。

#### External Boundary Layer（外部边界层）

系统与外部世界（OS、网络、其他进程）的交互边界。包含三个 package group：
- `packages/subprocess/` — 子进程管理
- `packages/client/connection/` — Browser ↔ Host 通信
- `packages/web/` + `packages/workflow/` — 网络请求和 Worker 隔离
- `packages/lsp/` — LSP server 生命周期

外部边界层的机制独立于 agent loop，它们可以被任何 consumer（无论是 agent 还是其他系统组件）使用。

#### Durable State Layer（持久状态层）

`packages/core/session/` 是整个系统可靠性的基石——它是唯一拥有"真相"的地方。Agent loop 向 session log 写入 event（`system/message`、`user/message`、`assistant/message`、`tool/call`、`tool/result`、`turn/start`、`turn/end` 等），所有的上层恢复机制都依赖 log 的完整性和可重建性。

Session projection cache 是这个层的附属优化组件——它不是 authority，只是 fold 的 shortcut。

**关键关系：** Session log 是唯一跨越所有层的纵向数据通道。从 Infrastructure Layer 的 atomic write（物理存储），到 External Boundary Layer 的 subprocess output 写入（tool result），到 Agent Loop Layer 的 turn/step event（生命周期），到 Agent Behavior Layer 的 retry event（恢复记录）——所有数据最终都落入 session log。

#### Agent Loop Layer（Agent 循环层）

`packages/core/agent-loop/` 和 `packages/llm/` 共同构成 agent 的运行时核心。这一层实现：
- **Agent 生命周期管理**：`create()` / `resume()` 的事务语义，`dispose()` 的 quiescence 保证
- **LLM 调用的可靠性**：错误分类 + retry policy 执行形成完整的故障恢复流水线

LLM retry 和错误分类体系的关系是 **上下游协作**：Error classification（`packages/llm/llm/`）定义 `HarnessError.code`，Provider adapter 将 HTTP 响应映射为标准 code；LLM retry（`packages/llm/llm-retry/`）作为 consumer 读取 code，根据 policy 决定是否 retry。

Cancellation 是 Agent Loop Layer 的"横切面"——它不是独立模块，而是贯穿 `create()`、每个 turn/step、`dispose()` 所有阶段的基础设施。

#### Agent Behavior Layer（Agent 行为层）

`packages/guard/` 是最接近模型交互的一层，作为 plugin 注册在 agent loop 的 waterfall 上，不改变 loop 的核心逻辑：
- **Tool timeout** 注册在 `tools/execute` waterfall 上，包裹每个 tool 调用
- **Loop detection** 注册在 tool call 提交点，监控重复调用模式

这两个 guard plugin 都通过 Cordis 的 plugin 注册机制 attach 到 agent loop，可以独立启用/禁用；它们彼此独立——tool timeout 关注单次调用的时长，loop detection 关注跨调用的模式。

#### Cross-cutting Concerns（横切关注点）

三个横切机制作用于所有层：
- **Defensive patterns**：编码规范层面，指导所有层的代码编写
- **Callback exception isolation**：在 Cordis event dispatch 框架层面，确保所有层的 listener 异常都被隔离
- **Runtime invariant**：每个关键 package 发布自己的 invariant companion plugin，在生产环境中持续验证该 package 的 contract

### 19.3 可靠性纵深防御总结

```
用户请求 → [Loop detection] → [Tool timeout]  ← Agent Behavior
                ↓                    ↓
           [LLM retry ← Error classification]   ← Agent Loop
                ↓
           [Cancellation / quiescence]
                ↓
           [Session log (append + crash repair)] ← Durable State
                ↓
    ┌───────┼───────┬──────────┬──────────┐
    ↓       ↓       ↓          ↓          ↓
[Process] [Conn]  [LSP]    [Proxy]    [DNS]    ← External Boundary
    ↓       ↓       ↓          ↓          ↓
    └───────┴───────┴──────────┴──────────┘
                    ↓
           [Atomic I/O + File lock]              ← Infrastructure
```

每一层只信任其下层提供的保证，并在自己的职责范围内增加新的可靠性属性：

1. **Infrastructure** 保证"写入不会被破坏"
2. **External Boundary** 保证"外部交互不会泄漏或失控"
3. **Durable State** 保证"任何时刻崩溃都可恢复到一致状态"
4. **Agent Loop** 保证"故障被正确分类、重试或终止，不扩散"
5. **Agent Behavior** 保证"模型级异常被检测和干预"

三条横切线贯穿全部五层：
- **Defensive patterns** 约束代码的正确性
- **Callback isolation** 保护 event 系统的完整性
- **Runtime invariant** 在生产中持续验证所有 contract

### 19.4 核心哲学

1. **Durable before action**：在任何外部 effect 之前记录意图，确保崩溃后可恢复
2. **Cooperative, not hard kill**：通过 signal 通知终止，而不是直接杀 process
3. **Fully reconstructable from log**：所有模型可见的状态都可以从 session log 中推导出
4. **Every dispose must reach quiescence**：不只是请求停止，而是 await 实际停止
5. **Fail loud, not silent**：misconfiguration 在 load time 被发现；runtime invariant 持续验证
6. **Each layer owns its failure domain**：通过 Cordis waterfall 和 typed event 干净组合
