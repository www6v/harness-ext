## 契约层（Contract Layer）

定义系统对调用者的承诺——无论内部发生什么，外部契约始终成立。

### ⭐ P1: Never-Reject 结果契约

**一句话定义**：异步操作发布后，其结果 Promise 永不 reject——所有失败扁平化为类型化的成功值。

**解决的问题**：级联故障。如果子操作的异常直接 propagate 到父调用者，一个子任务的崩溃会导致整个调用链断裂。

**核心实现**：

```
        异步操作完成/失败/取消
                │
                ▼
    ┌───────────────────────┐
    │   try { result }      │
    │   catch(err) {        │
    │     if (cancelled)    │
    │       → 'aborted'    │
    │     else              │
    │       → 'error'      │
    │   }                   │
    │   finally {           │
    │     collectOutput()   │
    │   }                   │
    │                       │
    │   返回值: {            │
    │     stopReason:       │
    │       'completed'     │
    │     | 'aborted'       │
    │     | 'error'         │
    │     output: string    │
    │     diagnostic?: str  │
    │   }                   │
    └───────────────────────┘
```

**子系统实例**：

| 系统 | 契约位置 | 停止原因类型 |
|------|----------|-------------|
| Subagent | `settleRunResult()` — 子 Agent 发布后 | `completed`, `aborted`, `error`, `max-tokens`, `refusal` |
| Workflow | `drive()` — Worker 脚本执行后 | `completed`, `cancelled`, `error` |

**设计要点**：
- `try/catch/finally` 覆盖所有路径，finally 确保 output 总是被收集
- 取消优先级高于异常——cancelled 在 catch 内外各检查一次
- 诊断信息有界（Subagent: 4096 字节，Workflow: 通过 `renderThrown()` 渲染）
- 停止原因是可扩展的联合类型——调用者精确匹配而非字符串比较

---

### ⭐ P2: 幂等操作

**一句话定义**：可能被多条路径触发的操作（回收、取消、结算），通过记忆化 Promise 或首次胜出策略保证副作用只发生一次。

**解决的问题**：在异步系统中，同一个操作通过多条代码路径被并发触发是常态而非异常。不幂等 → use-after-free、重复释放、状态不一致。

**核心实现**：

```
  路径 A          路径 B          路径 C
  dispose()      cancel()       workerDeath
      │              │              │
      └──────────────┼──────────────┘
                     │
                     ▼
         ┌─────────────────────┐
         │  记忆化守卫          │
         │                     │
         │  memo !== undefined? │
         │  → return memo      │  ← 返回已有 Promise
         │                     │
         │  memo === undefined? │
         │  → memo = doWork()  │  ← 首次调用，执行副作用
         │  → return memo      │
         └─────────────────────┘
```

**子系统实例**：

| 系统 | 幂等操作 | 记忆化方式 |
|------|----------|-----------|
| Subagent | `dispose()`, `inbox.close()`, `cancel()`, `settleResult()` | `let disposal: Promise \| undefined` / `this.settled` 守卫 |
| Teams | `cancel()` | 首个 reason 胜出 |
| Workflow | `dispose()`, `cancel()`, `settleResult()`, `endAgent()` | `disposed` Promise 记忆化 / `liveAgents` Map 去重 / 按 `callId` 去重 |

**设计要点**：
- 不同粒度的去重：整体操作去重（dispose）、按实体去重（按 callId 的 child dispose）、按序列号去重（endAgent 按 seq）
- `cancel(reason?)` 采用"首个 reason 胜出"策略——保留最原始的取消原因用于诊断
- 已结算/已声明终端的 run 被保护——cancel 不改变已确定的结果

## 控制层（Control Layer）

管理操作的生命周期——启动、执行、取消、回收的时序和并发控制。

### ⭐ P3: 有界取消

**一句话定义**：取消不是发一个信号就完事——它是覆盖多层级、带确定性截止时间的纵深防御体系。

**解决的问题**：单层取消不可靠——某个层级可能因状态卡住导致取消信号无法到达，或取消后无限等待清理完成。

**核心实现**：

```
  cancel() 被调用
      │
      ▼
  Layer 1: 幂等守卫（首个 reason 胜出）
      │
      ▼
  Layer 2: 信号传播（postMessage / AbortSignal）
      │
      ▼
  Layer 3-N-1: 各层级检查点（每个 await 后 throwIfCancelled）
      │
      ▼
  Layer N: 强制终止（grace timer 到期 → 合成结果 → 强制终结）
      │
      ▼
  子节点回收层: 启动前检查 + 子节点 AbortSignal 传播
```

**子系统实例**：

| 层级 | Subagent (5 层) | Workflow (7 层) |
|------|-----------------|-----------------|
| 幂等守卫 | — | cancel() 首个 reason 胜出 |
| 启动前 | signal aborted → 拒绝 start | Ready/Go 握手被 Cancel 替代 |
| 信号传播 | AbortSignal 贯穿所有接口 | worker.postMessage('Cancel') |
| 子节点传播 | 所有子共享 AbortController | 所有子共享 AbortController |
| 检查点 | 关键区段 throwIfAborted() | 每个 hook 入口 + 每个 await 后 |
| 强制终止 | 多级回收（stdinEOF→SIGTERM→SIGKILL） | disposeGraceMs(5s) + worker.terminate() |
| 滞留合成 | — | 为未结束 agent 合成 agent-end: cancelled |

**设计要点**：
- `disposeGraceMs`（默认 5s）保证取消有确定性的完成时间上限
- 所有 timer 都是 `unref()` 的——不阻止进程退出
- 取消后 `throwIfCancelled()` 在每次 yield 后强制检查——取消响应延迟不超过单次 await 耗时
- 子节点传播至关重要——父取消时子节点也必须停止，否则资源泄漏

---

### ◆ P4: 按实体串行化操作

**一句话定义**：对于给定实体（子 Agent、团队 Leader），所有变更操作通过 Promise 链强制串行，防止并发竞态。

**解决的问题**：同一实体的两个并发操作交错执行导致状态不一致——修订号跳跃、名称重复分配、半写状态被读取。

**核心实现**：

```
  ┌─────────────────────────────────────┐
  │   tails: Map<EntityId, Promise>     │
  │                                     │
  │   transact(entityId, async () => {  │
  │     await tails.get(entityId);  ← 等待前一个操作
  │     doWork();                       │
  │     await appendAndFlush();     ← 原子提交点
  │     notifyWaiters();                │
  │   })                                │
  │                                     │
  │   操作 A → 操作 B → 操作 C   (串行)   │
  │   不同 EntityId 之间并行             │
  └─────────────────────────────────────┘
```

**子系统实例**：

| 系统 | 实体粒度 | 实现 |
|------|----------|------|
| Subagent | 每个子 Agent (`ChildLock`) | `childId → Promise` 链，发送/释放/回收串行 |
| Teams | 每个 Lead (`TeamJournal`) | `leadSessionId → Promise` 链，所有变更串行 |

**设计要点**：
- 不是全局锁——不同实体之间零争用（Subagent 不同子 Agent 间并行，Teams 不同 Lead 间并行）
- 失败的关键区段不影响后续不相关的调用者（错误在链式 tail 中被吸收）
- `appendAndFlush()` 是原子提交点——flush（等价 fsync）后才通知等待者
- Promise 链利用 JS 事件循环的自然顺序，比互斥锁更轻量

## 状态层（State Layer）

管理状态的持久化、校验和恢复——保证状态在代码缺陷、进程崩溃和磁盘故障下始终一致。

### ⭐ P5: 事件溯源（Event Sourcing）

**一句话定义**：状态不直接存储，而是存储不可变的事件日志；当前状态通过确定性重放事件序列派生。

**解决的问题**：内存状态 + 磁盘状态的"双写"模式——缓存失效、写入顺序、部分写入都会导致不一致。

**核心实现**：

```
  ┌──────────────────────────────────────────┐
  │          Event Log (唯一真相来源)          │
  │                                          │
  │  [event₁] [event₂] [event₃] ... [eventₙ] │
  │     │        │        │            │      │
  └─────┼────────┼────────┼────────────┼──────┘
        │        │        │            │
        ▼        ▼        ▼            ▼
  ┌──────────────────────────────────────────┐
  │        fold(events[]) → State            │
  │                                          │
  │  确定性重放: 同样的事件序列 → 同样的状态     │
  │  每次读取都是一次从日志头的完整重放          │
  └──────────────────────────────────────────┘

  写路径: append + flush → 通知等待者
  读路径: fold(events) → 返回派生状态
```

**子系统实例**：

| 系统 | 日志内容 | 投影函数 |
|------|----------|----------|
| Subagent | `subagent/descriptor`, `subagent/catalog` | `foldSubagentDescriptor()` 重建 composition |
| Teams | `team/member`, `team/task`, `team/message/*` | `foldTeam()` 派生 roster + taskBoard + mailbox |
| Workflow | `workflow/start`, `workflow/agent-*`, `workflow/end` | 引擎层不变量 + 工具记录层不变量 |

**设计要点**：
- **仅日志事件（log-only events）**——协调事件不进入对话表面或模型可见历史
- **flush-before-notify**：任何观察到的状态变更在崩溃后一定可恢复
- **确定重放意味着无"幻读"**——给定日志内容，投影结果数学上唯一
- **版本化**：Teams 的 `stateVersion: 3`、Subagent 的 descriptor version，支持未来迁移

---

### ⭐ P6: 不变量强制（Invariant Enforcement）

**一句话定义**：在每条数据进入持久化存储之前，通过克隆-试应用-校验的管道拦截无效事件，防止状态污染。

**解决的问题**：代码缺陷导致无效事件写入唯一真相来源后，恢复难度指数级上升——越早拦截代价越低。

**核心实现**：

```
  候选事件
      │
      ▼
  ┌────────────────────────────┐
  │  ① structuredClone(state)  │  克隆当前投影
  └──────────┬─────────────────┘
             │
             ▼
  ┌────────────────────────────┐
  │  ② clone.apply(event)      │  试应用候选事件
  └──────────┬─────────────────┘
             │
      ┌──────┴──────┐
      ▼             ▼
   success       failure
      │             │
      ▼             ▼
  ┌────────┐  ┌──────────────┐
  │ 写入日志│  │ 拦截 + 报告   │
  └────────┘  │ 永不进入日志  │
              └──────────────┘
```

**子系统实例**：

| 系统 | 不变量层级 | 捕获的违规类型 |
|------|-----------|---------------|
| Teams | 单层（invariant companion） | 无效阶段转换、名称重用、修订号间隙、重复消息、DAG 循环、身份字段不可变违规 |
| Workflow | 双保险（引擎层 + 工具记录层） | agent-start/end 配对、身份快照一致性、run-end 前开放成员、尾部缺失 = 打断证据 |

**Workflow 双保险的互补关系**：

```
  引擎层不变量                    工具记录层不变量
  ────────────                   ────────────────
  校验时机: 实时 dispatch         校验时机: 冷加载 + 实时追加
  校验对象: 内存事件流            校验对象: 持久化 Session 记录
  严格性:   所有违规都是错误       严格性:   尾部缺失 = 打断（非损坏）
  
  如果引擎层漏过无效事件            如果磁盘损坏
  → 工具记录层冷加载时发现          → 版本检查 + schema 校验挡住
```

**设计要点**：
- 克隆后试应用——即使校验逻辑有 bug 也不会污染真实状态
- 捕获的是代码缺陷而非用户错误——每次触发都意味着有 bug
- 双保险互补：实时拦截 + 持久化发现，覆盖不同故障模式

### ◆ P7: 崩溃恢复（Crash Recovery）

**一句话定义**：进程重启后，通过重放持久化日志自动恢复中间状态（卡住的成员、未投递的消息、未完成的子 Agent），而非要求人工介入。

**解决的问题**：长时间运行的 Agent 操作中进程崩溃，所有进度丢失，且可能留下"幽灵"状态（成员卡在 provisioning、消息未投递）。

**核心实现**：

```
  进程重启 / agent:session-start
          │
          ▼
  ┌──────────────────────────────┐
  │  遍历日志中的"进行中"记录       │
  │                              │
  │  Subagent:                   │
  │  → 检查 descriptor 完整性     │
  │  → coldResume() 重建 Agent   │
  │                              │
  │  Teams:                      │
  │  → reconcileProvisioning()   │
  │    找到卡住的 provisioning    │
  │    → 验证子 session 完整性    │
  │    → active 或 failed        │
  │  → recoverFor()              │
  │    重放 queued - delivered   │
  └──────────────────────────────┘
```

**子系统实例**：

| 系统 | 恢复场景 | 恢复手段 |
|------|----------|----------|
| Subagent | Continuable 子 Agent 跨进程存活 | `coldResume()`: 从 descriptor 重建 + 校验 lineage |
| Teams | 队友 spawn 中途崩溃 | `reconcileProvisioning()`: 磁盘校验 → active/failed + 竞态处理 |
| Teams | 消息投递中途崩溃 | `recoverFor()`: 计算差值 → 按序重试 + 去重 |
| Workflow | N/A（脚本不持久化，有意不提供） | — |

**设计要点**：
- 恢复基于事件日志（P5）——不需要额外的检查点文件
- 竞态处理是关键：恢复和创建可能并发（如 HMR 场景），必须检测并决议
- 名称/ID 永不重用——防止恢复时将新实体与旧日志混淆
- 明确声明边界：Workflow 有意不提供脚本级检查点/恢复（设计权衡）

## 隔离层（Isolation Layer）

隔离故障传播、安全边界和身份验证——防止局部故障级联为系统故障。

### P8: 监听器/观察者隔离

**一句话定义**：每个事件监听器独立 try/catch，单个监听器的失败不影响其他监听器和事件发布者。

**解决的问题**：一个生命周期监听器抛出异常导致事件发布中断，后续监听器被跳过，回收流程被破坏。

**核心实现**：

```
  emit(event)
      │
      ▼
  for (listener of listeners) {
      try {
          listener(clonePayload(event))  ← 每个监听器独立 try/catch
      } catch (err) {                    ← 独立负载克隆
          log(err)                       ← 记录但不传播
      }
  }
  // 无论多少监听器失败，emit 总是成功返回
```

**子系统实例**：

| 系统 | 隔离位置 | 机制 |
|------|----------|------|
| Subagent | `createLifecycleEmitter()` | 每个 listener 独立 try/catch；rejected promise 独立捕获 |
| Workflow | `emitWorkflowEvent()` | 每个 listener 独立 try/catch + 独立负载 clone |

**设计要点**：
- 每个监听器收到独立的负载克隆——防止监听器之间通过修改负载互相影响
- 失败的监听器被记录（日志/警告）但不传播——事件发布者无感知
- Provider 移除事件不影响回收流程——保证 teardown 完整性

### ◆ P9: 跨边界安全序列化

**一句话定义**：在隔离域之间（vm ↔ 宿主、子进程 ↔ 父进程）传递数据时，严格校验并物化为纯 JSON，拒绝一切不可序列化的值。

**解决的问题**：跨域泄漏函数、Symbol、原型污染导致序列化崩溃或安全漏洞。

**核心实现**：

```
  ┌────────── 源域 ──────────┐
  │  {                        │
  │    name: "ok",     ← 通过 │
  │    fn: ()=> {},    ← 拒绝 │
  │    __proto__: {},  ← 特殊处理
  │    [Symbol]: "x",  ← 跳过 │
  │  }                        │
  └──────────┬────────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │  materialize / validate  │
  │                          │
  │  ✅ 纯 JSON 值            │
  │  ❌ Function / Symbol    │
  │  ❌ BigInt / undefined   │
  │  ❌ 循环引用 / 稀疏数组    │
  │  ❌ 异质原型链             │
  │  ⚡ __proto__ →           │
  │    defineProperty 安全化  │
  └──────────┬────────────────┘
             │
             ▼
  ┌────────── 目标域 ─────────┐
  │  { name: "ok" }          │
  │  安全的纯 JSON            │
  └──────────────────────────┘
```

**子系统实例**：

| 系统 | 边界 | 校验方式 |
|------|------|----------|
| Subagent | 启动时描述符快照 | 确保可无损 JSON 序列化后再启动 |
| Workflow | vm Realm → Host Realm | `materializeFromRealm()` 严格拒绝非纯 JSON 值 |

**Workflow 特有的安全问题**：
- `__proto__` 通过 `Object.defineProperty` 变为自有属性——防止原型污染
- Getter 正常运行但在物化时执行——抛出异常则大声失败
- 致命性通过 `instanceof` 跨域检查——脚本域构造的对象永远无法通过宿主域的 `WorkflowError instanceof` 检查

**设计要点**：
- 不是在序列化失败时处理——而是在值离开源域时就拦截
- 物化失败大声暴露而非静默截断——避免"部分数据丢失"的隐形 bug

---

### ◆ P10: 精确身份授权

**一句话定义**：不依赖可伪造的字符串 ID 做授权——使用精确的内存对象引用（`WeakSet<Agent>`）验证操作者身份。

**解决的问题**：`sessionId` 字符串可被重放攻击；过期或伪造的 Agent 身份可通过简单的 ID 比较绕过授权。

**核心实现**：

```
  操作请求到达
      │
      ▼
  ┌──────────────┐
  │ 准入控制      │  ← drain 期间拒绝新工作
  │ assertAdmitting│
  └──────┬───────┘
         │ 通过
         ▼
  ┌──────────────┐
  │ 血统验证      │  ← 检查精确的活跃 Agent
  │ authorize     │
  │ Lineage()     │
  └──────┬───────┘
         │
  ┌──────┴──────┐
  ▼             ▼
  Agent 在      Agent 不在
  WeakSet 中?   WeakSet 中?
  → 授权        → UNAUTHORIZED

  WeakSet<Agent> 绑定到内存对象引用
  过期/伪造的身份不可能在其中
```

**子系统实例**：

| 系统 | 授权机制 | 独特设计 |
|------|----------|----------|
| Subagent | 准入控制 + 血统验证 | `WeakSet<Agent>` 追踪祖先；`ownedChildren` 防止父在有子时结算 |
| Teams | 精确 Agent 身份 | Lead/成员角色分离；每个服务方法接受精确 Agent 凭证 |

**设计要点**：
- `WeakSet<Agent>` 而非 `Map<sessionId, ...>`——内存引用不可伪造
- 准入控制在 drain 期间阻止新工作——没有它优雅关闭不可能
- `holdOwnership()` 预注册——在子创建前就占位，失败路径自动释放
- 分层授权：第一层准入（是否可以操作），第二层血统（是否有权操作此特定实体）

---

## 防御层（Defense Layer）

纵深防御和降级策略——在部分组件故障时保持系统可观测、可恢复。

### P11: 纵深防御（Defense in Depth）

**一句话定义**：对同一威胁部署多道独立防线——每道防线有不同的失效模式，一道被突破不影响其他防线。

**解决的问题**：单道防线有盲区——运行时校验可能被绕过，持久化校验只在加载时执行，信号传播可能因状态卡住而失效。

**核心实现**：

```
  ┌─────────────────────────────────────────────┐
  │              威胁: 状态损坏 / 取消失败         │
  └────────────────────┬────────────────────────┘
                       │
     ┌─────────────────┼─────────────────┐
     ▼                 ▼                 ▼
  Line 1            Line 2            Line 3
  实时不变量        持久化不变量       启动前校验
  (dispatch 时)     (加载/追加时)     (start 时)
     │                 │                 │
     ▼                 ▼                 ▼
  防止无效事件      发现持久化损坏     防止已取消启动
  进入日志          识别尾部打断      执行脚本
```

**子系统实例**：

| 系统 | 防御层级 | 各层职责 |
|------|----------|----------|
| Workflow 取消 | 7 层 | 幂等守卫 → postMessage → AbortController → grace timer → 强制终止 → 启动前检查 → 每 await 检查 |
| Workflow 不变量 | 2 层 | 引擎层（实时拦截）+ 工具记录层（持久化发现） |
| Subagent 回收 | 3 层 | stdin EOF → SIGTERM → SIGKILL（进程外子节点） |

**设计要点**：
- 每层有不同的失效模式——postMessage 可能丢消息，但 AbortSignal 不依赖消息传递
- 最后一层总是强制终止（grace timer + terminate）——保证最终一定停止
- 双不变量互补：实时校验严格（所有违规都是错误），持久化校验智能（区分损坏和打断）

---

### ◆ P12: 优雅降级（Graceful Degradation）

**一句话定义**：当部分组件失败时，不尝试重试或恢复——而是留下"合法但截断的"状态记录，供用户和系统做出明智的后续决策。

**解决的问题**：写入重试可能产生时序交错的损坏数据；完全放弃则不留下任何可观测信息。

**核心实现**：

```
  正常路径:                      降级路径:
  ────────                      ────────
  event₁ ✅                      event₁ ✅
  event₂ ✅                      event₂ ✅
  event₃ ✅                      event₃ ❌ ← 首次失败
  event₄ ✅                              │
  event₅ ✅                      ┌───────┘
  = 完整记录                      │
                                 ▼
                          禁用后续所有写入
                          (一次警告)
                                 │
                          event₄ ✗
                          event₅ ✗
                          = 合法连续前缀
                            (非损坏!)
```

**子系统实例**：

| 系统 | 降级场景 | 降级行为 |
|------|----------|----------|
| Workflow | Session 日志追加失败 | 首次失败后禁用后续写入 → 合法连续前缀 → `interrupted` 状态 |
| Teams | 消息投递失败 | 消息留在队列中 → `queued` 返回值 → 下次恢复时重试 |
| Subagent | 子 Agent 列表枚举时某子损坏 | 该子产生诊断行 → 不阻塞整体列表加载 |

**设计要点**：
- **选择"合法截断"而非"损坏"**——这是关键的可靠性设计权衡
- **一次警告而非告警风暴**——失败后的静默不淹没日志
- **`interrupted` 状态的诚实性**——UI 从缺失事件诚实派生，而非猜测
- **部分结果可被查看**——已完成的 agent 输出没有丢失
- **用户有足够信息决策**——展示最后成功操作 + 停止原因 → 用户可以查看结果/重新运行/手动继续


**依赖关系**：
- P5（事件溯源）是 P6（不变量）、P7（崩溃恢复）、P12（优雅降级）的基础——它们都依赖事件日志作为唯一真相来源
- P4（按实体串行化）是 P6（不变量）的使能器——不变量校验需要一致的状态投影，而串行化保证状态在读取时的完整性
- P1、P2、P3 三者共同构成"操作的确定性终局"——无论发生什么，操作总有确定的结果（P1），多条路径触发同一操作不会重复执行（P2），需要终止时一定能在有限时间内终止（P3）
- P8、P9、P10、P11 构成系统的隔离和安全边界——故障不传播、安全不越界

## 何时使用哪个模式

| 场景 | 推荐模式 | 原因 |
|------|----------|------|
| 构建异步操作的外部 API | ⭐ P1: Never-Reject | 防止级联故障，调用方始终拿到确定性结果 |
| 操作可能被多条路径触发 | ⭐ P2: 幂等操作 | 异步系统的现实：cancel + timeout + error 都可触发回收 |
| 需要取消长时间操作 | ⭐ P3: 有界取消 | 单层取消不可靠，必须有截止时间 |
| 同一实体有多个并发写入者 | ◆ P4: 按实体串行化 | 防止丢失更新、修订号间隙、名称重复 |
| 需要跨进程保存状态 | ⭐ P5: 事件溯源 | 免除缓存失效问题，确定重放无幻读 |
| 数据完整性是关键需求 | ⭐ P6: 不变量强制 | 在污染前拦截，克隆试应用防止二次损坏 |
| 需要进程重启后恢复 | ◆ P7: 崩溃恢复 | 基于 P5 的日志重放，需处理并发恢复的竞态 |
| 有多个观察者/回调 | P8: 监听器隔离 | 一个失败不影响其他，不影响事件源 |
| 跨隔离域传递数据 | ◆ P9: 跨边界安全 | 防止不可序列化值泄漏，防止原型污染 |
| 需要授权/访问控制 | ◆ P10: 精确身份授权 | 字符串 ID 可伪造，内存引用不可伪造 |
| 关键操作需要防失效 | P11: 纵深防御 | 不同失效模式用不同防线覆盖 |
| 写入路径可能失败 | ◆ P12: 优雅降级 | 合法截断 > 损坏 > 空白 |
| 构建 agentic 系统中的任何可靠性机制 | ⭐ P5 + P1 + P2 | 这三个是所有其他模式的基础 |

## 总结

DeepSeek Harness 的可靠性设计不是一套零散的技巧，而是 12 个相互关联、分层协作的设计模式。它们共同构成了系统的可靠性骨架：

```
  契约层 (⭐P1-⭐P2):         对调用者的承诺永不违背
  控制层 (⭐P3-◆P4):         生命周期确定、有序、有界
  状态层 (⭐P5-⭐P6-◆P7):    状态一致、可校验、可恢复
  隔离层 (P8-◆P9-◆P10):      故障局限、安全不越界
  防御层 (P11-◆P12):         多层防线、损而不坏
```

其中 ⭐ 标记的 5 个模式（P1, P2, P3, P5, P6）为**基石模式**——被至少两个子系统同时使用，缺失任何一个都会导致系统可靠性崩溃。◆ 标记的 5 个模式（P4, P7, P9, P10, P12）为**重要模式**——解决关键场景问题，系统在特定条件下可降级运行但不完整。其余 2 个模式（P8, P11）为辅助模式，增强已有机制的韧性。

这 12 个模式的核心权衡是一致的：**宁可有界失败也不无限等待，宁可大声暴露也不静默吞掉，宁可合法截断也不产生损坏，宁可拒绝操作也不允许越权。**
